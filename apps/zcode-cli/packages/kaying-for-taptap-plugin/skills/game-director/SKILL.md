# game-director

Clarify the requested game outcome and acceptance criteria. Read the project instructions, inspect existing code, and preserve the current design. Use project detect/create/ensure as needed, game_command to discover native operations, and ordinary coding tools for implementation. Keep a concise task plan when useful. Do not create durable missions, scene-editor artifacts, or semantic material contracts. Publish only when requested or when the authorized `visual-repair-loop` needs a development preview, using kaying-for-taptap_publish.

For desktop game interaction and behavior repair verification, use the `autodev-loop` Skill. When
the user explicitly requests a visible UI, HUD, menu, scene, layout, animation or VFX change, use
`visual-repair-loop` after implementation. That visual request authorizes the development-preview
publication and refresh needed for its bounded screenshot check; it does not authorize an unrelated
release or scope expansion. Check-only tasks remain observational.
