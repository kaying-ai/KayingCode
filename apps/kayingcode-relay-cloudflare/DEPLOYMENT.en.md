# Relay first-deployment guide

[中文（默认）](DEPLOYMENT.md) | **English** · [Overview](README.en.md) · [Implementation](IMPLEMENTATION.en.md) · [Flows](FLOWS.en.md)

Reviewed: 2026-11-07. Deploy Relay, automatic identity authorization and the Web workbench on one Worker and HTTPS origin. All domains below are placeholders. Run commands from the repository root unless stated otherwise.

## 1. Prerequisites

- Node 24.14.0 and pnpm 10.31.0, as pinned in mise.toml. Omit mise exec -- only if those versions are already activated.
- Git, the repository and locked dependencies. Web builds export a pinned official Git commit; uploading only this application directory is insufficient.
- A Cloudflare account with permission to deploy Workers, assets and SQLite-backed Durable Objects. Check current account quotas/billing; this guide does not promise a particular price or plan.
- Select the actual external origin, such as https://relay.example.com. Your workers.dev address can be used initially. Browser, Desktop and built assets must use the same service.

```sh
mise install
mise exec -- pnpm install --frozen-lockfile
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare exec wrangler login
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare exec wrangler whoami
```

CI can inject Cloudflare's CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID from its secret store. Do not commit credentials. Desktop generates and stores its identity automatically; users do not provision accounts or enter credentials.

## 2. Configuration

| wrangler.jsonc field     | Current value / action                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| name                     | kayingcode-relay-cloudflare; choose the Worker name for this service                                     |
| main / compatibility     | src/index.ts, 2026-10-13, nodejs_compat; use the tested configuration                                    |
| durable_objects.bindings | WEB_REMOTE → WebRemoteRelayObject                                                                        |
| migrations               | Use the DO initialization configuration shipped with this project; no manual lifecycle setup is required |
| assets                   | ./public, ASSETS, run_worker_first:true; generated by the build                                          |

The service uses Cloudflare Worker, static assets and SQLite-backed Durable Objects. Wrangler provisions the namespace on first deployment using wrangler.jsonc. The application selects the upstream-v2 named object. Deploy the supplied configuration together with the code.

In the Cloudflare dashboard, select the Worker and configure a Custom Domain under Settings / Domains & Routes. Your domain must meet Cloudflare zone/DNS requirements. Complete domain binding after the initial deployment, then validate HTTPS. See [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

## 3. Local development and validation

```sh
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare typecheck
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare test
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare test:integration
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare dev
```

dev builds Web before starting local Wrangler, normally at http://127.0.0.1:8787; use the printed address. HTTP is for local interface debugging. Formal Desktop invitation links use HTTPS. A local HTTP process is not real-device QR acceptance. The embedded Web origin must match the environment being tested; its default comes from packages/web/upstream-web.json, not an automatic localhost override.

Integration uses a free temporary port, isolated SQLite state and REMOTE_V2_TEST_ORIGIN. Cleanup stops only the test-owned process tree and deletes its temporary state. It covers real HTTP/WS, roles/SID, replay, leases, logout, assets and both notice hashes. Worker-dependent cases may be skipped when running test alone.

For an intentional local reset, stop Wrangler, then run `mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare dev:reset`. This removes the application's local .wrangler/state accounts, devices and invitations. It is neither an upgrade step nor a production recovery command.

## 4. Build and publish

Use the final external origin. Choose the appropriate shell.

POSIX:

```sh
KAYINGCODE_REMOTE_ORIGIN=https://relay.example.com mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare deploy
```

Windows PowerShell:

```powershell
$env:KAYINGCODE_REMOTE_ORIGIN = "https://relay.example.com"
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare deploy
Remove-Item Env:KAYINGCODE_REMOTE_ORIGIN
```

deploy publishes to Cloudflare. Replace deploy with build:web for a local asset build. After build:web, inspect a local Worker bundle with:

```sh
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare exec wrangler deploy --dry-run --outdir .wrangler/dry-run
```

The actual sequence is build:web → clear/copy public → wrangler deploy --keep-vars. keep-vars preserves existing remote ordinary variables; it does not set the build-time origin. Dashboard runtime variables cannot repair an address already compiled into JavaScript. The origin is public configuration, not a secret. Changing it requires rebuilding, deploying and aligning Desktop.

### 4.1 Review or controlled-deployment lifetimes

Normal deployments keep the defaults: a five-minute, single-claim invitation and a 30-day terminal credential. For app-store review or internal demos that need two to four weeks and several reviewers, deploy a **separate review Worker and origin** instead of relaxing production limits.

Set these as ordinary variables on that Worker (Cloudflare dashboard → the Worker → Settings → Variables and Secrets; they are not secrets):

| Variable                              | Review example | Purpose                                   |
| ------------------------------------- | -------------- | ----------------------------------------- |
| `KAYINGCODE_REMOTE_INVITE_TTL_DAYS`   | `30`           | Invitation valid for 30 days              |
| `KAYINGCODE_REMOTE_INVITE_MAX_CLAIMS` | `5`            | Allow up to five claims from one link     |
| `KAYINGCODE_REMOTE_TERMINAL_TTL_DAYS` | `30`           | Each claimed credential valid for 30 days |

Durations use days and accept fractions (`0.5` means 12 hours). Variables affect newly issued invitations only. Existing invitations keep the `expiresAt` and `remainingClaims` recorded when issued, so lowering the configuration does not shorten existing links. Invalid or out-of-range values fall back to defaults without blocking the service.

Build and deploy an isolated review Worker (replace `review.example.com`):

```sh
KAYINGCODE_REMOTE_ORIGIN=https://review.example.com mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare run build:web
mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare exec wrangler deploy --name kayingcode-relay-review --keep-vars
```

`--name` overrides the Worker name in wrangler.jsonc; the review Worker gets its own Durable Object namespace. Bind the review domain to that Worker in the Cloudflare dashboard, then add the variables above. Delete the review Worker/domain after review; at minimum delete devices, stop remote control and remove the variables.

Point the review Desktop at the review origin and use an isolated data directory so the production owner identity is not reused:

```sh
export KAYINGCODE_OFFICIAL_CLOUDFLARE_RELAY_ORIGIN=https://review.example.com
export KAYINGCODE_DATA_BASE_DIR=/srv/kayingcode-review
```

`build:web` writes the review origin into `packages/web/dist` and `public/`. Rebuild with the production origin before any production deployment.

Generate public through build:web and deploy it as a build artifact. packages/web/upstream-web.json pins the official source. Missing Git objects are fetched without moving the product branch. The manifest contains source, relayOrigin and audit hashes. Both third-party notices ship with assets. Material verification is explicit rather than a requirement to clear the entire backlog before packaging; see [license policy](../../third-party/SPEC.md).

## 5. Desktop and mobile onboarding

For self-hosting, set the following origin before launching Desktop:

```powershell
$env:KAYINGCODE_OFFICIAL_CLOUDFLARE_RELAY_ORIGIN = "https://relay.example.com"
```

On POSIX: `export KAYINGCODE_OFFICIAL_CLOUDFLARE_RELAY_ORIGIN=https://relay.example.com`. Launch the actual Desktop application from that environment. System-icon/background launches must inherit it too; no installation path is assumed here. Packaged Desktop reads the process environment first, then the desktop package's `.env` snapshot, and only then falls back to the default production origin.

If KAYINGCODE_WEB_REMOTE_CONTROL_URL or KAYINGCODE_WEB_REMOTE_CONTROL_RELAY_WS_URL overrides are configured, align them with the same deployment. Usually the origin setting is sufficient.

1. Open a local workspace in Desktop and enable remote control from the mobile entry at the lower left.
2. Desktop registers owner/device and generates the complete `/remote/v4?sid=…#authorize=…` link and QR code.
3. Scan or paste the complete link into a browser. SID alone or a bare page URL cannot authorize the first session.
4. The browser claims an independent credential and opens the workbench. Refresh the Desktop QR if the invitation expired or was consumed.
5. Taro/Flutter self-hosted entry points open that same full URL with authorization handled by the browser. Native upstream ZCode OAuth is a separate channel.

Desktop, Host and workspace must remain available. Relay cannot run an Agent on behalf of an offline desktop. Clearing browser storage loses the locally saved terminal credential and requires authorization again; server logout revokes its digest.

## 6. Acceptance

Use curl.exe in PowerShell if curl is aliased; use curl on POSIX:

```sh
curl --fail https://relay.example.com/healthz
curl --fail https://relay.example.com/readyz
curl --fail https://relay.example.com/remote/mobile-web-manifest.json
curl -I https://relay.example.com/remote/v4
curl -I https://relay.example.com/remote/THIRD-PARTY-NOTICES.md
curl -I https://relay.example.com/remote/UPSTREAM-THIRD-PARTY-NOTICES.md
```

healthz/readyz should be 200. v4 should serve directly without redirecting away its route. manifest.relayOrigin must match the external origin. Anonymous GET /api/v1/remote/device is 401; /v1/client-config, /v1/nodes and /admin/ are 404. Readiness proves storage readability, not Desktop availability, pairing or task execution.

Use a dedicated test workspace for a real mobile scan, existing sessions, send/reply, refresh recovery, disconnect/reconnect, same-role replacement, logout, mobile layout and branding. Compare both notice files with manifest.notices hashes. Record local automation and production real-device acceptance separately.

## 7. Routine maintenance

Record the deployed Worker version, Git commit, external origin and Web manifest. Publish matching Worker and assets together. When diagnosing a failure, check origin, readiness and the Desktop connection first; use Cloudflare version management to restore a known matching version when appropriate. Code rollback does not restore DO data.

Use the checked-in wrangler.jsonc as the service configuration. Rebuild Web when changing the external origin. Local dev:reset only affects local test data.

References: [Wrangler deployment and versions](https://developers.cloudflare.com/workers/wrangler/commands/workers/), [Durable Objects configuration](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/).

## 8. Troubleshooting

| Symptom                                  | Investigation / action                                                                                    |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| healthz 404, domain or TLS failure       | Check Worker, Custom Domain/route, DNS and actual origin                                                  |
| readyz 503                               | Inspect WEB_REMOTE binding, class export, migrations and Cloudflare logs                                  |
| v4 or static JS 404                      | Verify build:web, public/ASSETS and SPA fallback; rebuild for the correct origin                          |
| Invitation expired/used                  | Refresh Desktop QR; preserve an existing independent browser credential rather than replaying invitations |
| HTTP 401/403, AUTH_FAILED                | Separate long-lived bearer from ticket; check owner/device versus terminal, account and SID/MID           |
| waiting / DEVICE_OFFLINE                 | Confirm Desktop is online, SID matches and both sides completed auth_init                                 |
| KICKED / repeated replacement            | Look for tabs/clients competing for the same SID/role                                                     |
| Missing messages after reconnect         | Inspect Host snapshot/resync and the existing session; Relay has no offline queue                         |
| Old service accessed after domain change | Rebuild Web and check manifest, Desktop environment and old browser sessions                              |

Observe Worker logs with `mise exec -- pnpm --dir apps/kayingcode-relay-cloudflare exec wrangler tail`. Do not add logging of credentials, full invitation URLs, token queries or business payloads.
