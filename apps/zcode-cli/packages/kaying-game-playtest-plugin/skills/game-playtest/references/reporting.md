# 结构化评价

## 默认交付：新游戏试玩报告

evaluation 报告面向尚未亲自玩过游戏的读者。读完应能回答：这是什么游戏、什么设计风格、
玩家具体做什么、一局怎样推进、哪里有趣、关卡奖励通向什么、适合什么偏好的玩家。
以游戏和玩家为主语，用自然的介绍和具体例子组织正文。不要将命令回执、模拟器、工具耗时、
验证覆盖率写成文章主线，也不要把“支持 Metal”“工具成功执行”当作游戏亮点。

### 文风与篇幅

像玩过后给朋友讲重点。先说判断，再给一个看得见的细节，不从“本次采集到……”开场。

- **篇幅**：导语一句话；正文通常约600–900字，不含图注、结构化问题和附录。普通章节
  约40–90字，核心玩法/一局体验必要时可到120字。修订长报告时，各节以原文约一半为目标，
  先删重复再缩句；短节不强行对半，不能删掉影响结论的条件。用户指定篇幅优先。
- **条理**：每节选1–4个值得关注的点，按重要程度排列，通常2–3点就够。多点用
  `1. …\n2. …` 逐行写入 section.text，每点只说一件事、1–2句，不加嵌套列表；
  只有一点直接写一句，不凑满四点。保留现有十二章，不把整篇强改成四章。
- **真人感**：用“提示挡住了两行图块，提前看落点不方便”这样的观察说明判断。
  少用“完成度高、情绪通路自然、形成闭环、具有策略空间”等缺少具体含义的评价；
  可用“我试了一次……”交代真实选择，但不要每节都自述。不添加未体验的情绪或经历。
- **取舍**：规则只完整解释一次。删操作坐标、逐步计数、界面物件清点、无关资源余额；
  它们只有在解释规则或问题时才进入正文。不要用“不是行业创新，但……”为亮点铺垫。
- **边界**：未体验项集中到 coverage，涉及推测处仍写“只看到入口”等必要限定，
  不能把装扮入口写成实际玩过装扮。包名、设备详情、输入统计、工具故障留在附录。
- **图注**：一句话指出看点，不重讲段落、不清点素材；此前来源照常注明。轻松不等于广告腔，
  不强行卖萌、不堆感叹号，不写无依据的“上头、必玩、停不下来”。

传 gameName 和 lede：前者用于“游戏名｜新游戏试玩报告”标题，后者用一句话交代
类型、题材和最值得关注的体验。十二个 key 保持稳定，正文按以下顺序呈现：

| key             | 面向读者的内容                                                          |
| --------------- | ----------------------------------------------------------------------- |
| summary         | 一句游戏定位，不照抄导语；不混入测试进度                                |
| information     | 名称、版本/平台、类型、操作形式；包名和设备详情放附录，不猜收费方式     |
| audiovisual     | 最有辨识度的1–2处视觉细节及观感；未听音频在 coverage 统一说明           |
| mechanics       | 操作、目标、关键规则与限制；术语在这里解释一次，奖励去向只写已验证部分  |
| onboarding      | 教学怎么带玩家动手、是否容易跟；不复述按钮路径和整套规则                |
| gameplay        | 一次真实选择及反馈；不逐步记账，没打完就不写成完整一局                  |
| innovation      | 哪个具体设计让体验更好、为什么；不重新介绍规则，不夸成行业创新          |
| retention       | 实际玩到的成长内容；只看到入口就直接说明，不列货币余额或推断长期留存    |
| issues          | 直接点出影响；已有结构化问题时，正文一句概括，不重复步骤/预期/实际/建议 |
| recommendations | 适合哪类玩家及理由；需要继续确认的内容集中到 coverage                   |
| evidence        | 配图/短片值得看哪里，一句即可；不重复玩法、不清点截图数量与采集过程     |
| coverage        | 到了哪一关/阶段、哪些关键体验未涉及；目标、动作、故障和计时放附录       |

每个亮点必须有实际观察支撑。介绍画面看到的成长入口不等于验证了长期留存；
不要由货币图标推断收费、由第一关推断整个游戏难度、由同类机制推断创新性。
正文保留有意义的范围说明，避免每一段机械重复“本轮未验证”。

### 基于 Fishdom 快速试玩报告的改写示例

以下只示范文字取舍，实际提交仍要检查原证据并附 evidenceIds；不是其他游戏的默认结论。

原“一局体验”逐步记录交换坐标、步数29→27→26，再说“有一点策略空间”。可压缩为：

> 1. 第2关先教做爆竹，再让玩家点爆；清掉一片后，图块落下继续连锁，反馈接得很快。
> 2. 随后试了一次普通三消，也顺利触发补位。这里只玩了开场几步，还看不出后续难度。

原“亮点”用“爆炸感、治愈感、情绪通路”串联尚未体验的养成。改成具体且有边界的判断：

> 爆竹教学很直观：刚做出的道具马上就能点爆，作用一眼看得见。鱼缸装扮只看到入口，暂不评价。

原“了解范围”混入13次输入、ADB、服务进程回收等技术复盘。可压缩为：

> 1. 玩到第2关开场，试了普通三消、生成爆竹和引爆，还没打到结算。
> 2. 音效、商店付费、装扮和后续关卡未体验，暂不评价。

### 提交前自检

1. 扫一遍每节开头，能否直接读到重点？多点是否逐行编号、每点只讲一件事？
2. 同一规则是否跨章重讲？正文是否重复图注或结构化问题？删掉重复部分，不换词再说一遍。
3. 长段是否压到原文约一半？删除一句后若不影响理解，就删；短节不为凑篇幅添加内容。
4. 判断是否有具体细节支持，且仍区分“实际玩过、只看到入口、未体验”？保留必要限定，
   把设备统计、工具故障移回附录。改写不新增操作、不改原始证据，也不替未测试维度打分。

为关键章节提供 media:[{artifactId,caption}]，引用该章节 evidenceIds 中的真实图片/视频。
通常选2–4张有区分度的画面和2–3个短片：整体风格、核心棋盘/操作、成长任务、代表性反馈。
配图与解释放在一起；不要把全部截图按时间堆到文章末尾。此前试玩画面须实际检查并 attach，
图注和了解范围注明来源，不能写成当次新体验。无需为了修改报告文风重新游玩。

Runtime 将评分、置信度、验收目标、计时、环境、日志及完整证据置于默认折叠附录。
正文不添加逐章“依据与来源”段落或来源链接，图注保留必要的此前素材说明；
evidenceIds 照常提交，引用与原始材料在 JSON 和附录中保留。
diagnostic 仍用于运行诊断。原始证据、字段和评价修订保留，不能为了文章好看补造结论。

所有 MCP 工具的完整参数以 `tools/list` 返回的 schema 为准。`report_generate.review`：

- `gameName`：读者看到的游戏名称；`lede`：游戏介绍导语，不含工具/设备验收信息。
- `sections`: `{key,text,certainty,evidenceIds,media?}` 数组。key 为 summary、information、coverage、
  mechanics、onboarding、gameplay、audiovisual、retention、innovation、issues、evidence、recommendations。
  certainty 为 observed（实际观察）、inferred（合理推断）、unverified（未验证）。
  可选 status: verified/partial/blocked/not-tested/not-applicable；未测试原因写在 text 中。
  media 的每项为 `{artifactId,caption}`，只能引用该章节证据中的截图/录像/高光。
- `scores`: `{dimension,score,confidence,reason,evidenceIds}` 数组。dimension 为 gameplay、
  onboarding、controls、visual、audio、stability、retention、innovation；score 为 0–10 或 null，
  confidence 为 0–1。没体验过为 null，不能给 0。总分按已覆盖维度等权换算 100 分，
  必须和覆盖率、置信度一起阅读；单一维度 10 分不代表游戏得到完整 100 分评价。
- `issues`: `{title,severity,steps,expected,actual,recommendation,evidenceIds}` 数组。
  severity 为 P0（完全阻断/崩溃）、P1（核心体验严重受损）、P2（局部体验问题）、P3（轻微建议）。
  steps 是非空步骤数组；涉及等待的结论记录实际时间，不能随意声称“5 秒无响应”。

每次传 review 缺省按章节 key/评分 dimension 合并，issues 提供时整体替换；
只有 reviewMode=replace 才整体替换，历史保存于 reviewRevisions。原始操作、事件、媒体不变。
reportKind=diagnostic 不呈现综合游戏评分；评分维度覆盖率与目标验证数分开。
report_generate 返回 qualityWarnings；交付前补足已有证据的分析，无法覆盖时说明原因。
运行耗时的 unattributedActiveMs 不能称为纯模型思考时间；不可由少量样本宣称 GPU 加速倍数。
已覆盖内容必须引用本会话返回过的 artifact id，不能用文件名或虚构 id。运行时只检查引用
存在，Agent 仍须亲自检查内容是否支持结论。可以先不传 review 输出明确未覆盖的部分报告。

示例（用真实返回的 ID 替换占位符）：

```json
{
  "sections": [
    {
      "key": "mechanics",
      "text": "拖动棋子进入目标格后出现成功提示。",
      "certainty": "observed",
      "evidenceIds": ["真实截图ID"]
    }
  ],
  "scores": [
    {
      "dimension": "controls",
      "score": 7,
      "confidence": 0.7,
      "reason": "三次拖动中一次缺少落点提示；只覆盖第一关。",
      "evidenceIds": ["真实截图ID"]
    }
  ],
  "issues": []
}
```
